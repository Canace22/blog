起因是 Claude Opus 5.5 发布时，官方特别强调了「缓存读取降价 60%」（$0.50 → $0.20 / 百万 token），而输入价只降了 20%。为什么缓存读取的降价更值得关注？顺着这个问题把 Prompt Caching 整理了一遍。

## 一、它是什么

每次调 API，都要把完整上下文发过去：系统提示、工具定义、历史对话、读过的文件……模型每次都要从头处理一遍，按输入 token 收费。

但这些内容大部分每次都一样。Prompt Caching 就是让服务端把这段重复的**前缀**存起来，下次请求开头一样时直接复用。

以 Claude 为例，有两个计费项：

- **缓存写入**：第一次存进去，比普通输入稍贵
- **缓存读取**：之后命中缓存，价格只有普通输入的 1/20 左右

## 二、为什么对 Agent 特别重要

Agent（比如 Claude Code、Codex）跑一个任务要来回调几十上百次模型，每一轮都带着前面全部上下文，而且越来越长。

粗算一下：上下文 10 万 token，跑 50 轮，按 Opus 5.5 价格——

- 不缓存：500 万输入 token × $4 = **约 $20**
- 命中缓存：首次写入约 $0.5，后面 49 轮读取约 $1，合计 **约 $1.5**

Agent 的账单大头往往是「反复读同一段上下文」，所以缓存读取的价格才是关键。

## 三、核心原理：前缀匹配

**从第一个 token 开始比，遇到第一个不同的地方，后面的缓存全部作废。**

记住这一条，下面所有策略都是它的推论。

## 四、提高命中率的策略

**1. 不变的放前面，变的放后面**

Claude 的拼接顺序是 `tools → system → messages`。固定内容（工具定义、系统提示、参考文档）放前，用户新消息放最后。

最常见的坑：在系统提示里写当前时间、随机 ID、用户名。一改就全部失效。这类信息放到最后一条消息里。

**2. 保证序列化稳定**

「意思一样」不够，要**字节一样**：

- 工具列表顺序固定，不要动态排序或按条件增减
- JSON key 顺序固定
- 空格、换行的拼接方式保持一致

**3. 历史只追加，不修改**

每轮只在末尾加新消息。删中间某条、截断早期消息、改写前文，都会让之后的缓存失效。需要压缩上下文时，一次压一大段，别每轮裁一点。

**4. 断点放对位置（Claude）**

Claude 需要手动用 `cache_control` 标断点，最多 4 个。常见放法：

- 系统提示末尾放一个
- 对话最后一条消息放一个，每轮往后挪（增量缓存）

```js
messages: history.map((msg, i) =>
  i === history.length - 1
    ? { ...msg, content: [{ type: "text", text: msg.content, cache_control: { type: "ephemeral" } }] }
    : msg
)
```

**5. 注意过期时间**

Claude 默认 5 分钟，命中会续期。调用间隔可能超过 5 分钟（比如等人工确认）就用 1 小时缓存。

**6. 会话中途别换东西**

切模型、改工具列表、改思考参数、增减图片，都会让缓存无法复用。

**7. 并发前先预热**

同时发 10 个请求，大家都等不到缓存建好，结果 10 个都在写入。先发一个建好缓存，再并发。

**8. 太短不缓存**

有最小长度要求（一般一千多 token 起，各模型不同，以官方文档为准）。

## 五、怎么验证命中

| 平台 | 看哪个字段 |
|---|---|
| Claude | `usage.cache_creation_input_tokens`（写入）、`usage.cache_read_input_tokens`（命中） |
| OpenAI | `usage.prompt_tokens_details.cached_tokens` |

可以跑这几个测试：

1. 同一请求连发两次 → 第二次应该有命中
2. 系统提示里加时间戳 → 命中归零（验证动态内容会破坏缓存）
3. 多轮对话 → 第 N 轮命中数 ≈ 第 N-1 轮的总输入
4. 等超过过期时间再发 → 重新写入
5. 调换两个工具的顺序 → 命中归零

## 六、各家有什么不同

**原理都一样（前缀匹配），上面的策略通用。** 不同的是开启方式和计费：

| | Claude | OpenAI（Codex） |
|---|---|---|
| 开启 | 手动标 `cache_control` | 默认自动，也支持显式断点 |
| 写入费 | 比普通输入贵 | 不收 |
| 过期 | 5 分钟 / 1 小时 | 内存模式 / 扩展模式最长 24 小时 |
| 额外控制 | — | `prompt_cache_key` |

OpenAI 的几个要点：

- **`prompt_cache_key` 很关键**。OpenAI 是把请求路由到最近处理过相同前缀的机器上，这个 key 帮它把相关请求送到同一处。GPT-5.6 及之后的模型必须设置它才能用更可靠的匹配。按用户或会话设一个稳定值即可。
- 简单理解：**Claude 是告诉它「缓存到这里」，OpenAI 是告诉它「这些请求是一伙的」**。
- 多轮 Agent 优先用 Responses API，据说缓存利用率比 Chat Completions 高不少。

其他家（Gemini、DeepSeek、Kimi 等）大多也有自动前缀缓存，Gemini 另有需手动创建、按存储时长收费的显式缓存。具体以各家文档为准。

**一个坑**：通过 OpenAI 兼容接口（比如某些中转网关）调 Claude，可能用不上 Claude 的缓存，要走原生接口。

## 七、结论

- 用 Claude Code、Codex CLI 这类官方工具：缓存它们自己处理，不用管。
- 自己调 API：**保持前缀稳定**是通用原则；Claude 记得标断点，OpenAI 记得设 `prompt_cache_key`。
- 算成本时，Agent 场景重点看缓存读取价格，而不只是输入输出价格。
